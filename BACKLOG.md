# Backlog

Active queue of work that's been thought through and parked, not work-in-progress. Items leave this file by being done, being filed as an ADR/OpenSpec change, or being decided as won't-do.

For historical context (pre-v0.20 design audits and exploration notes), see `todo.md`. For shipped work, see `CHANGELOG.md` and `docs/adr/INDEX.md`.

## How this file works

- One section per category (governance, tooling, ADRs, framework features, etc.).
- One bullet per item. Lead with what triggers picking it up; not when.
- If an item is conditional on a real signal (e.g. "ADR count exceeds 30"), state the trigger inline.
- Items that get picked up move to a commit + ADR/OpenSpec/CHANGELOG entry, then disappear from here.
- No dates. The order is by significance within a section, not chronology.

## Governance + process

- **Round-12 doctrine validation.** ADR 0005 predicts that future a2web rounds will surface fewer re-litigations and more retract-before-submit behaviour as C3 (misdiagnosis self-check) takes hold. Round 12 is the validation test. If the round is materially smoother, the doctrine holds. If not, revisit which clause failed and amend with a follow-up ADR.
- **Sibling doctrines if other consumer types emerge.** The current doctrine assumes a small set of close, named downstream consumers. If an external contributor pattern emerges (anonymous bug reports, third-party plugin authors), the doctrine needs either an update or a sibling document. Trigger: first non-named-consumer filing.
- **Promote deferred items from archived changes into BACKLOG in the same commit.** When `/opsx:archive` lands a change with deferred sub-tasks, those items SHALL be added as BACKLOG bullets in the archiving commit. Otherwise the follow-ups live only inside `openspec/changes/archive/<dated>/tasks.md` or `decisions.md` and are invisible to anyone reading BACKLOG. Trigger: any future archive whose tasks.md contains a "Deferred to follow-up" section. Implementation candidate: an `opsx:archive` post-hook that scans the archived change for deferred markers and refuses to archive unless the listed items have BACKLOG entries.

## Framework features

- **Nested CLI layout flag (`CliConfig.layout`).** From `native-tree-homomorphism` (§5/§7) — the CLI already renders the nested `app <slug> <leaf>` layout (panels per router); the structured `router_slug` + `leaf` stay on the descriptor so a flat `app slug_leaf` rendering is a purely presentational flag-flip. The door is kept reachable but the flag is not enabled. Trigger: a consumer wants flat top-level CLI commands instead of slug sub-groups. Cross-ref: `openspec/changes/archive/2026-06-09-native-tree-homomorphism/design.md` §5.

- **Transport-neutral extension verb (Thread E).** `AppBuilder` carries two transport-specific composition verbs — `add_cli(group)` and `add_mcp_middleware(m)` — on an otherwise transport-neutral composition root. Generalising them to a single `add_extension(transport, obj)` was considered during `split-app-builder-runtime` and **deferred** (ADR 0016, design D5): with exactly two explicit single-purpose verbs, a generic `add_extension` would reintroduce the polymorphic dispatch the project deliberately removed (`core-composition`'s "three named verbs"). The generalisation pays off only at a third transport. Trigger to pick up: a third transport adapter is added (e.g. the REST surface below). At that point, revisit whether three+ transport verbs justify the generic form.

- **REST surface — sibling of the code-execution change.** `docs/VISION.md` Phase 1: a REST / OpenAPI surface projected from the same tool definitions, unlocking the remote-REST and remote-CLI modes. **Binding constraint:** code execution is never exposed on REST — the `code-execution` capability spec carries `### Requirement: Code execution is never exposed on the REST surface`, which this change must honour (no `execute` route, no code endpoint, no discovery meta-tools). Trigger to pick up: the REST spike lands and de-risks the type-driven OpenAPI projection.

- **AGENTS.md drift policy.** Once AGENTS.md is the canonical agent-instruction file, decide whether CLAUDE.md stays as Claude-specific overlay or symlinks to AGENTS.md. Trigger: a Claude-specific behaviour that AGENTS.md cannot capture cleanly. Until then, current split is the default.

- **`fold-dispatch-pipeline-on-http`.** Precondition for re-opening `unify-signature-installers` (archived SUPERSEDED 2026-05-25). Today the HTTP path's `install_substrate_signature` wraps `fn` from scratch and folds nothing; the MCP path folds the transport-neutral dispatch pipeline (timeout → enrichers → router-lazy-enter → dispatch-hook+DI → ldd-state → error-capture). Folding the pipeline on HTTP gains ldd ambient / format routing / error capture on FastAPI (desirable on its own merits) and makes both paths "fold pipeline + relabel signature," at which point one signature-relabel function handles both surfaces. Trigger: pick up whenever the §2-no-redundancy debt note (ADR 0020 §Consequences) becomes load-bearing OR ldd ambient becomes wanted on HTTP. Cross-refs: `openspec/changes/archive/2026-05-25-unify-signature-installers-SUPERSEDED/decisions.md`, ADR 0020 amendment.

- **`add-auth-jwt` follow-up.** Sibling to the landed `add-auth` MVP. Adds `JwtAuth` dataclass + JWKS fetcher with TTL caching + ASGI middleware on `/api`. New optional dep group: `python-jose` + `httpx`. Parallels `APIKeyAuth` shape exactly; the registry already filters by `target="api"`. Trigger: first consumer wanting SSO sharing identities between MCP OAuth and HTTP. Cross-ref: `openspec/changes/archive/2026-05-25-add-auth/tasks.md` (§4).

- **`add-auth-google-oauth` follow-up.** Sibling to `add-auth` MVP. Adds `GoogleAuth` wrapper around `fastmcp.server.auth.providers.google.GoogleProvider` + the `build_mcp_server` hand-off that passes `auth=` to FastMCP. `PrincipalMiddleware` already lifts `Context.access_token` into the request contextvar, so the path is short. Trigger: first consumer wanting MCP OAuth on a deployed server. Cross-ref: `openspec/changes/archive/2026-05-25-add-auth/tasks.md` (§5).

- **Registry-driven `expose=` validation.** Today `_verbs._validate_expose` hardcodes `{"mcp", "api"}` because `_verbs` lives in L2 authoring and `SURFACE_REGISTRY` lives in L4 dispatch — reading the registry from L2 would violate `A2K-LAYER`. Two viable paths: (a) relocate `SURFACE_REGISTRY` to a lower layer (kernel candidate; it has zero a2kit deps), or (b) move expose validation into the runtime layer (`app.py:_build_descriptors` already reads `extras.expose`, can validate against registry there). Trigger: a third surface is added beyond `mcp` / `api`, OR a third-party wants to register one. Cross-ref: `openspec/changes/archive/2026-05-25-remove-substrate-literal/tasks.md`.

- **README "Authentication" section.** Short section pointing at `APIKeyAuth`, the `App.auth(...)` registration, the `authorize=` kwarg, and the `auth.testing` seam. Defer the section's third paragraph (JwtAuth + GoogleAuth) until those land. Trigger: pick up alongside the first auth-follow-up change so the README lands in one pass.

- **Sub-configs via DI when env mutation hurts.** Today `McpConfig` / `HttpConfig` / `CliConfig` / `LddConfig` are reached as `app.config.<sub>` at composition seams (middleware, CLI builder, dispatch stages — all places where `app` is already in scope). The provider-chain (ADR 0022) is about who *sets* config values, not how subsystems *receive* them, so DI vs attribute access is orthogonal to the consumer-beats-code invariant. Converting to `provides=[McpConfig]` etc. is ceremony without payoff today: every existing reader is 1-2 lines, and tests that need config variation already work via env mutation (which is the path consumers actually use, so testing it is correct). Trigger to pick up: a test where env mutation is the wrong surface (concurrent races on env, property-based tests varying config many times per run), OR a subsystem that needs config + another container dep in one resolve and threading both through App becomes uglier than one DI call. Until then, attribute access is fewer moving parts. When picked up, scope the change as a single-pass conversion of all existing sub-config readers — a half-converted codebase is worse than either end state.

- **Migrate a2web to the `a2kit.log` surface + call-log (full, not just sinks).** Supersedes the older "migrate a2web sinks" note — `refound-ldd-on-stdlib-logging` (ADR 0027) is a far bigger break than the sink promotion. a2web migration covers: (1) **rename** `a2kit.ldd.event(TierEnded(...))` → `a2kit.log.info(TierEnded(...))` across the 28 typed-emit sites (instance rides the level method; no `event()` verb) — `fetcher.py` (22), `browser.py` (2), `llm_eval/runner.py` (4); (2) env `A2KIT_LDD__*` → `A2KIT_LOG__*`; (3) drop hand-ported `events/sinks.py` (otel/live now framework built-ins); (4) adopt the call-log — turn on `A2KIT_LOG__CALL_LOG`, log bodies via `a2kit.log.debug("html", html=...)` / `debug("md", md=...)` (file-only by level, correlated by `call_id`), and **retire the hand-written `fetch_result.json` / `answer.txt` / `row.json` I/O dump** (the call-log auto-captures ask+result; bodies ride debug). NO `a2kit.journal`, NO `record()` verb — enrichment is debug logging. CAVEAT (consumer audit 2026-05-29): the call-log subsumes the *I/O dump only* — eval-harness metadata (`cost_usd`, `cache_hit`, `extraction_model`) is computed outside dispatch, so it stays a2web enrichment correlated by an explicit `call_id`, not auto-capture. Trigger: after `refound-ldd-on-stdlib-logging` lands in a2kit. Cross-ref: `openspec/changes/refound-ldd-on-stdlib-logging/`.

- **Port remaining extension surfaces to `PluginManifest`.** From `adopt-plugin-manifests` (2026-05-27 archive). The framework module + API-key pilot landed; remaining drift-prone surfaces still re-discover the registration / unavailability / capability-check pattern: (a) connections (`packages/connections/`) — credentials presence varies, perfect fit; (b) future auth providers (`JwtAuth`, `GoogleAuth` — drop them in `packages/auth/_providers/jwt.py` etc. with their own `MANIFEST`); (c) code-mode tools; (d) `expose=` validation (registry-driven; see `A2K-SURFACE-REGISTRY` lint below). NOTE: log sinks were a candidate here but were DROPPED 2026-05-29 — `refound-ldd-on-stdlib-logging` decided NO manifest for sinks (YAGNI; sinks aren't user-extensible today, and `add_sink()` covers the rare custom case). Re-open only on the trigger below. Trigger: pick up per surface when its next change lands. Each migration is mechanical: add `_providers/` subpackage, move construction into a factory, declare `MANIFEST`, switch the call site to `load_surface(...)`. The architecture invariant (`tests/capabilities/plugin_manifest/test_manifest_module_no_import_side_effects.py`) already parametrises over discoverable provider dirs — extend the discovery glob to cover new surfaces as they land.

- **`http-render-stage-and-surface-middleware-spec`.** From `STRUCTURE_ISSUES.md` open smells S7 + S11 + S13 + R13's post-mortem (2026-05-27). The dispatch pipeline is substrate-neutral on paper (ADR-0019), but middleware-shaped cross-cutting concerns are re-implemented per substrate today. The two surfaces have drifted: `packages/http/` is one builder + 5 install helpers in `build.py`; `packages/mcp/` is one builder + 5 standalone `Middleware` classes (`format_routing`, `guards`, `listview`, `principal_middleware`, `_wrappers.TypedErrorEnvelopeMiddleware`). Same five concerns (build, typed-error envelope, auth/principal, request-scope, render/format, authorize gate), divergent shapes. S11 is the concrete driver: HTTP is missing the typed-render-stage pattern entirely. Bundle scope: extract a transport-neutral `SurfaceMiddleware` (or pipeline-stage) protocol both substrates honor, then add the render stage once. Closes S7 (shallow DecoratorSurface), S11 (HTTP render parity), S13 (duplicated AuthorizeGateStage on HTTP). Trigger to pick up: when something blocks on HTTP not having format-routing, OR a third substrate lands. Needs `/opsx:explore` before shaping. Estimate: 2-3 weeks, regression-risky (touches every request-path error/render/auth flow on both substrates). Honest caveat: the "third substrate" forcing function is hypothetical today; S11 alone may be too small to motivate the bigger spec.
