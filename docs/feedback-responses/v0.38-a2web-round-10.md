## Friction A — test-harness boilerplate

**A1 `a2kit.testing.lazy(value)` — accepted.** Trivial helper, matches
existing `a2kit.testing` surface (`null_context`, `peek`, `client`).
Will ship as `a2kit.testing.lazy`. Constructor form, not `Lazy.of` —
keeps `Lazy` as a pure `TypeAlias` with no runtime attributes.

**A2 ambient fixture — accepted in fixture form only.** We will ship
`a2kit.testing.ambient_for_tests` as an importable pytest fixture
(consumer opts in via `pytest_plugins` or local re-export).

We're **rejecting the parenthetical alternative** ("silent no-op
outside dispatch with `A2KIT_LDD_STRICT=1`"). That inverts the
loud-by-default contract (`AmbientContextMissing` exists specifically
to fail loud); flipping polarity to silent-unless-env-var violates the
"no silent errors" principle. Opt-in fixture preserves the contract
and gives you the ergonomics.

**A3 `await a2kit.testing.resolve(app, T)` — shipped.** Was
over-cautious on the original park. The "scope CM design" concern
turned out to be a non-issue: resources resolved via
`Container.get(T)` already record cleanup on the appropriate
scope's stack (root for SINGLETON, child for SCOPED). For tests
already inside `async with app:` (or
`async with a2kit.testing.client(app):`), the existing lifespan
close drains everything — no new scope construct needed.

`a2kit.testing.resolve(app, T)` is a 3-line async sibling of
`peek`, wrapping `await app.container().get(type_)`. Matches the
existing helper-pair naming convention. Your `make_default_state`
collapses to:

```python
async with a2kit.testing.client(app) as c:
    state = await a2kit.testing.resolve(app, AppState)
```

(pairs naturally with the now-shipped `lazy-in-factory-params`
change — your `AppState` factory can take `Lazy[T]` fields, and
`resolve` walks the chain.)

## Friction B — `ctx: ToolContext` ceremony

**Shipped** as `relax-ldd-ambient-requirement`. The earlier draft of
this response proposed a per-router `emits_ldd` marker; on further
reflection we landed on the simpler answer below.

### A correction on our own model first

While scoping this we did a reading-only spike of the actual
dispatch path and found our own mental model was wrong in one
important way. **Ambient state is already bound unconditionally
on every framework-dispatched tool.** See
`packages/mcp/server.py:55-99` and `packages/cli/runtime.py:61-82` —
both transports enter `ldd_state_for_call(...)` for every
dispatch, regardless of signature.

What `ctx` in the signature actually controls is the **value of
ambient `ctx`** — non-None when declared, None when not. LDD
primitives check ambient `ctx is None` and raise
`AmbientContextMissing` Mode B (`missing_ctx_param`).

So the `del ctx` ceremony exists to make ambient `ctx` non-None
so LDD primitives don't raise Mode B. The friction is real;
we just had it framed wrong on our end.

### Why we're not adopting your proposed fix

1. **Spooky-action ergonomics (still the strongest argument).** A
   phase function four call-frames deep emits
   `a2kit.ldd.event(...)`. With unconditional per-tool synthesis,
   the caller's signature carries no signal that the call is
   inside a dispatch. With the marker we're proposing, the signal
   sits one level up (the router class) — still discoverable in
   one read, at the right granularity (consumers already group
   LDD-emitting tools by router).

2. **Wire-side cost.** For MCP transport, ctx synthesis means
   keeping a synthesized parameter in the rewritten wrapper
   signature so fastmcp injects ctx. Doing this unconditionally
   wastes the slot when the tool truly has nothing to do with
   ambient state (a pure read-only probe, a no-side-effect
   transform). The marker says "this router's tools want ambient
   ctx" — coarser than per-tool, finer than per-app, exactly
   right for how consumers group LDD work.

(Our earlier draft of this response had a third argument about
standalone DI — withdrawn after the spike. Standalone DI never
enters the dispatcher path, so it's unaffected by either choice.)

### What shipped — unconditional ambient ctx

The framework wrapper now synthesizes a non-None ambient `ctx` for
**every** dispatched tool, regardless of whether the tool's body
declares `ctx`. No marker, no per-router opt-in, no new public
surface. LDD primitives find non-None ambient ctx and emit
normally; tools that declared ctx still receive it as a kwarg
(today's behavior preserved); tools that didn't declare it never
see the synthesized parameter (the wrapper pops it before
invoking the body).

a2web's case: every `del ctx` line can be deleted. Tools that
don't use ctx in the body drop the param entirely.

Why we walked back the per-router marker:

1. The marker patched a problem the framework created for itself.
   Mode B raise was a self-inflicted gate on what is fundamentally
   a framework concern (whether to wire ctx into ambient state).
2. LDD = Log-Driven Development. Sink emission (structured logs
   persisted for post-hoc AI-agent diagnosis) is the primary
   contract; wire emission is secondary live UX. Gating ALL LDD
   on wire-side availability was incidentally wrong.
3. The "spooky-action ergonomics" concern was weak — phase
   functions already emit LDD without surface signal; the tool's
   signature ctx was implementation noise, not a documentation
   contract. Removing it changes nothing readers were relying on.

The original `add-router-ldd-marker` proposal was scrapped before
implementation. `relax-ldd-ambient-requirement` is what shipped.

## Friction C — canonical public surface depth

**Working as designed — closing.**

The depth isn't friction; it's intentional signal.
`a2kit.packages.di.Lazy` tells you Lazy lives in the DI subsystem.
Flat re-export to `a2kit.Lazy` erases that signal and starts a
re-export treadmill (next round it's `LddEmission`, then sink
protocols, then connection primitives, then…). The top-level
namespace is deliberately capped at the 95% authoring surface (see
`__init__.py:14` comment) and we're holding that line.

A correction on the feedback: `a2kit.testing.client` **already
exists** at `src/a2kit/testing.py:18`. If the prescribed pattern in
a2web's CLAUDE.md still routes through `a2kit.packages.testing.client`,
that's a stale doc, not a missing re-export.

If shorter imports matter inside a2web specifically, a local shim
(`_a2kit_imports.py` aliasing the symbols you touch most) is a
project-local fix that doesn't grow the framework's public surface.

The `_thread`/`threading` analogy was misleading — `a2kit.packages`
is not underscored, not pretending to be private, and not slated to
be. We don't want to commit to the rename either; the layout is the
layout.

## Friction D — `a2kit.desc(...)` sugar

**Rejected.** Direct violation of principle 2 (no multiple ways of
doing the same thing). The rationale for retiring `a2kit.Param` in
v0.31 — owning a description primitive duplicates pydantic — applies
identically to `desc`. Same shape, same problem.

If router verbosity matters, it's an editorial fix in a2web (extract
param `Annotated` aliases to module constants, group by tool, etc.),
not a framework primitive.

## Friction E — `Lazy[T]` fields on `AppState`

**Accepted as Interpretation B; shipped.** Earlier draft of this
response rejected E based on the "resolve-on-attribute-access"
reading. On a second pass we noticed two distinct interpretations
were tangled in the same ask:

- **Interpretation A** — `state.browser_pool` reads as a fully-
  resolved `BrowserPool` via descriptor magic. Attribute access
  with side effects. Still **rejected** — implicit-magic that
  reprs / debuggers / introspection accidentally trigger.
- **Interpretation B** — the field stores the `Lazy[T]` thunk
  itself; caller does explicit `await state.browser_pool()`. No
  magic. Field is just storage for the lazy handle.

Looking at the framework code: `Container.resolve_params` already
honored `Lazy[T]` for tool kwargs, but `Container._construct_kwargs`
(the factory-construction path) did NOT — `Lazy[T]` parameters on
a factory raised `UnresolvableType` at first resolution. This was
**spec-vs-implementation drift**, not by design — the
`di-conditional-injection` spec already promised both tool AND
factory recognition (line 8: *"Tool and factory parameters
annotated `Lazy[T]`... SHALL be recognized"*).

Shipped under `lazy-in-factory-params`:

- `_construct_kwargs` mirrors the `Lazy[T]` branch from
  `resolve_params` (~6 lines).
- `_validate_scope_graph` rejects SINGLETON factory with
  `Lazy[per-call-T]` — the captured closure would pin per-call
  types to root's cache; loud-fail at `async with app:` with
  a migration hint.

Your `AppState` can now look like:

```python
@dataclass(slots=True)
class AppState:
    settings: AppSettings
    breakers: AsyncCircuitBreakerFactory
    proxy_pool: ProxyPool
    sqlite: SqliteResource
    browser_pool: Lazy[BrowserPool]
    llm_extractor: Lazy[LlmExtractorResource]

def make_state(
    settings: AppSettings,
    breakers: AsyncCircuitBreakerFactory,
    proxy_pool: ProxyPool,
    sqlite: SqliteResource,
    browser_pool: Lazy[BrowserPool],
    llm_extractor: Lazy[LlmExtractorResource],
) -> AppState:
    return AppState(settings, breakers, proxy_pool, sqlite,
                    browser_pool, llm_extractor)

app.provide(AppState, make_state)
```

Tool signature collapses to `state: AppState, ctx: ToolContext`.
Phase functions take `state` and unwrap at the call site (`await
state.browser_pool()`).

The "resolve-on-attribute-access" interpretation (A) stays rejected.

## Friction F — health-check `_ensure()`

**Spike done. Doc-only fix, no new API.**

Reading-only spike on 2026-05-15 traced the path:

```
run_checks (packages/health/__init__.py:74)
  └─ _run_one_check (line 100)
      └─ app._container.resolve_params(check.fn)        (line 108)
          └─ Container.get(T) per kwarg
              └─ _construct                              (container.py:507)
                  └─ _enter_lifecycle                    (line 530)
                      └─ resource.__aenter__()
```

The `_run_one_check` docstring already documents this behaviour
(*"Routes through the v0.36 resolver so app-scope `__aenter__`
runs on first resolution... Health checks declaring a resource as
a parameter trigger entry of that resource"*). The contract is
real; it just lives in a private docstring instead of a capability
spec.

### Important nuance the spike surfaced

a2web's `SqliteResource` is almost certainly registered as a
**singleton** via `app.singleton(...)`. Singleton resources are
entered on first resolution **anywhere in the app** (a tool
dispatch, an earlier health check, anything) and exit at app
shutdown via `Container.aclose()`. They are NOT entered/exited
per health-probe invocation.

So the guarantee is precisely:

- By the time your check body runs, the resource has been
  entered. Whether *this* probe entered it or an earlier call
  did — you don't need to care.
- `await sqlite._ensure()` is redundant; the resolver already
  entered the resource.

We'll spec this under `clarify-health-check-resource-entry` —
pinning test + new Q in `OPERATIONAL_CONTRACTS.md`. No
`warm_up()` primitive. Consumer fix: delete the `_ensure()`
lines.

## Appendix — what the spike corrected on our end

Two material errors in our first-pass response, both caught
before any code was written:

1. **B's mental model**: we initially described the existing
   rule as "ambient binds iff ctx in signature." Wrong —
   ambient state binds **unconditionally** on every dispatch
   (`packages/mcp/server.py:55-99`, `packages/cli/runtime.py:61-82`).
   `ctx` in signature only controls whether ambient *ctx* is
   non-None. The Router marker therefore controls "ambient ctx
   synthesis when the tool body omits ctx," not "ambient
   binding." Functionally equivalent for a2web's purposes, but
   the implementation path is materially different
   (synthesize `_a2kit_ctx` parameter into rewritten signature
   so fastmcp injects).

2. **F's exit semantics**: we initially planned to spec
   `__aexit__` firing per probe. Wrong for the typical case —
   singletons exit at app shutdown, not per probe. The pinning
   test in `clarify-health-check-resource-entry` codifies the
   real singleton semantics (one enter across N probes, exit
   at lifespan unwind).

Sharing both for visibility — your feedback is good enough to
catch us when we're imprecise, but we want to be clear about
where our first read was off.
